## #333：混淆状态含义，修复建议可能恢复原故障

源码：`besfd/src/runner/adaptor/brn_adp_bt_avrcp.c`，行号均对应原 head。

- 15–24 行已有说明：手机暂停时仍可能传输无声 A2DP 流。研发截图进一步说明本次设备行为：发送 pause 后 A2DP/AVRCP 仍可能上报 playing，再播放不能仅凭缓存状态去重。这是真机反馈，静态核对没有独立复现实验。
- `__paused` 在 pause 成功后设 true（130–137），start 成功后设 false（122–129）；日志称其为 `pause_sent`（109）。它记录本地命令意图，不是要求与 A2DP 流实时相等的副本。
- 因此 PLAYING 条件中的 `|| __paused` 有明确用途。删除它或恢复只看 `__play_state` 的去重，会再次拦截“手机已暂停、流仍 playing”时的恢复命令。原报告第三条建议应撤回。
- “PAUSED 且 playing=false 时不更新标志导致 toggle 错误”缺少后果证据：toggle 在 191–192 行基于 `(playing && !__paused)`，当 playing=false 时，无论标志为何值都会选择 PLAYING。协议上报状态由 `avrcp_onPlayStatus`（453–468）更新，不能建议命令路径直接伪造上报状态。
- “去重取消导致抖动/协议错乱”没有提供重复命令非幂等的实现证据，也未证明实际触发链。最多是待验证风险，不能标注为已证实 P2；本次核对不宣称所有下游调用已证明幂等。

## 共同根因

当前自动评审输入包含完整 unified diff 和 commit log，但 read_diff 只能重读补丁；没有完整文件、调用者、页面注册、API 实现及产品契约。缩短提示词后，模型把“完整 diff”误当作“完整语义上下文”，产生控制流补全、按名称猜功能、把异步状态误认为必须同步等推断。报告把这些假设放进 findings，再以“有条件通过”触发失败门禁（Result.Passes 只接受“通过”），所以即便没有 P0/P1 仍可能阻断。

## 本次修正

提示词增加证据校准：不猜外层控制流、不虚构页面/合法值、不混淆命令意图与异步状态、建议不得恢复原故障、重复调用必须有实际错误后果证据。仅有假设时不写 findings，不因普通 diff 上下文有限自动给出有条件通过。输入截断、模型执行失败及已证实严重问题仍保持阻断。

这没有把代码阅读能力扩展为全仓搜索，也没有按关键词过滤结果、直接接受研发反馈或把历史失败状态改成成功。后续如需要证明跨文件问题，应另行增加固定 SHA 下的有界只读上下文；当前版本只对给定证据作结论。
