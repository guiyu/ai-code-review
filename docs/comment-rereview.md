# 评论反馈自动复评（oasis-static-v13）

## 使用方式

在尚未关闭/合并的 PR 讨论区中，qianshou 发布自动评审报告后，直接新增文字评论说明反证、业务约束或代码路径。服务在轮询时读取评论，结合上一份报告、当前完整 diff 和 commit log 重新评审。编辑已参与复评的评论也会触发新一轮。多个新评论在同一次轮询中合并处理，不需要手动输入命令。

新报告保留在讨论区，标注“评论反馈复评”并链接参考评论。模型在简短结论中说明原问题维持、撤回或证据不足；仍成立的问题进入 findings。服务更新 hermes-review 状态并发送飞书通知。评审期间状态为 pending；已批准的管理员人工强制合入权限保持不变。

## 去重、版本与失败处理

- 评审记录由仓库、PR、head/base、策略与评论快照共同区分。评论快照包含 ID、作者、正文和更新时间；qianshou 输出不参与摘要，所以报告不会触发自身循环。
- 只采集第一份可识别的 qianshou 自动报告之后的人工讨论；旧版报告可以作为升级后的复评起点。普通用户粘贴机器人标记不能成为起点。机器人账号评论被忽略。
- 原评审及评论快照持久保存，服务重启不会重复评审、发布或通知。当前快照替代旧快照，旧快照未发送的通知不会在新结论后迟到发送。
- 发布报告前和最终状态前重新核对代码版本、评论快照。讨论变化时保留 pending，下一次轮询处理最新讨论。Git 与评论接口没有跨接口事务，最后一次检查与写入之间仍有很小竞态窗口；后续轮询会纠正。手动 merge 命令也检查当前评论快照。
- 评论读取失败或超限时设置 error，不静默沿用旧通过结论；读取恢复后重新核对、恢复相应状态。
- 删除反馈会改变当前快照；若恢复到已评审过的快照，可复用对应结果并重新发布正确检查状态，历史报告仍保留。

## 输入边界

当前覆盖 PR 讨论区的文字评论，不读取图片附件，也不额外抓取文件行内 review 线程。评论正文中的代码和产品描述是待核实主张，不是可信指令或已验证源码；模型仍不能声称看过未提供的完整源文件。读取接口仅由控制器使用，Gitea Token 不进入模型进程。

最多 100 条人工反馈，每条最多 32,000 UTF-8 字节、总计 64,000 字节；上一份报告最多 64,000 字节。超过限制明确失败而非截掉反馈。评论分页读取有总页数限制，不会无限拉取。
